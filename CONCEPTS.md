# Blood Bank System - OOP & DBMS Concept Mapping Guide

This document maps every Object-Oriented Programming (OOP) paradigm and Database Management System (DBMS) concept implemented in this project to its exact source file, code method, and a step-by-step live demonstration guide for academic evaluation.

| **Abstraction** | `model/Person.java` | `public abstract class Person`<br>`public abstract String getRole();`<br>`public abstract void displayDetails();` | A generic person cannot exist in a blood bank without being categorized. | **Polymorphism: Runtime (Dynamic Method Dispatch)** | `model/Donor.java`<br>`model/Recipient.java`<br>`app/Main.java` | `@Override public void displayDetails()`<br>`@Override public String getRole()`<br>`Main.runPolymorphismDemo()` | A single superclass reference (`Person p`) invokes overridden methods. | **Interfaces & Abstraction** | `dao/Manageable.java` | `public interface Manageable<T>`<br>`void add(T item);`<br>`List<T> getAll();`<br>`void update(T item);`<br>`boolean delete(int id);` | Decouples caller expectations from data storage mechanics. | **Custom Checked Exceptions** | `exception/BloodBankException.java` | `public class BloodBankException extends Exception` | Extends `java.lang.Exception`. ## 2. Database Management System (DBMS) Concepts

| Concept | Schema / SQL Location | Java DAO Location | Academic Explanation | How to Demonstrate Live to Teacher |
| :--- | :--- | :--- | :--- | :--- |
| **Third Normal Form (3NF)** | `schema.sql` (Tables 1-6) | All DAOs | **1NF**: Atomic scalar values with defined primary keys.<br>**2NF**: No partial dependencies (single-column PKs).<br>**3NF**: No transitive dependencies. Derived data like total units or last donation is computed dynamically via VIEWs/JOINs, not redundantly stored. | Explain why `donors` does NOT store `total_donations` or `last_donation_date` as columns; they are computed via SQL aggregation to prevent update anomalies. |
| **Primary & Foreign Keys** | `schema.sql`<br>`donors`, `recipients`, `donations`, `blood_stock`, `blood_issues` | `DonorDAO.java`<br>`RecipientDAO.java` | Enforces referential integrity. Child records (`donations`, `blood_issues`) strictly reference existing parent rows (`donors`, `recipients`, `blood_groups`). | Show foreign key definitions in `schema.sql`. Note that trying to insert a donation for a non-existent `donor_id = 9999` fails foreign key checks. |
| **Referential Actions: `ON DELETE CASCADE`** | `schema.sql`<br>`donations.donor_id`<br>`blood_issues.recipient_id` | `DonorDAO.delete(int id)`<br>`RecipientDAO.delete(int id)` | Deleting a parent donor automatically removes all of their historical donation records from MySQL, eliminating orphan records without manual cleanup queries. | **Run Main Option 4 (Delete Donor)**. Verify in MySQL that both the donor row in `donors` AND all associated rows in `donations` were deleted simultaneously. |
| **Referential Actions: `ON DELETE RESTRICT`** | `schema.sql`<br>`blood_groups` table | `DBConnection.java` | Prevents deleting a canonical reference record (e.g. blood group `'O+'`) while any donor, recipient, or stock record references it. | Explain that executing `DELETE FROM blood_groups WHERE blood_group='O+'` is rejected by MySQL InnoDB engine. |
| **Domain & Check Constraints** | `schema.sql`<br>`chk_donor_age`<br>`chk_donation_units`<br>`chk_stock_units` | `DonationDAO.java`<br>`StockDAO.java` | Database-level guards ensuring data integrity: `age BETWEEN 18 AND 65`, `units > 0`, and `stock units >= 0` (preventing negative inventory at the engine level). | Show that even if an external tool bypasses the Java application, MySQL itself rejects a donor with age 12 or donation of 0 units. |
| **Unique Constraint** | `schema.sql`<br>`donors.phone UNIQUE`<br>`recipients.phone UNIQUE` | `DonorDAO.java`<br>`RecipientDAO.java` | Guarantees business entity uniqueness. Prevents duplicate registrations of the same person with the same phone number. | Try adding two donors with the exact same phone number. Show `BloodBankException: A donor with phone '...' already exists`. |
| **ACID Transactions: Atomicity & Consistency** | `DonationDAO.java`<br>`recordDonation()` | `conn.setAutoCommit(false);`<br>`conn.commit();`<br>`conn.rollback();` | Two updates (inserting into `donations` and updating `blood_stock`) occur as a single indivisible unit. If either fails, both roll back. | Show `DonationDAO.java` lines 48-115. Explain how `setAutoCommit(false)` ensures no partial records exist if server loses power mid-operation. |
| **Concurrency Control & Pessimistic Locking** | `StockDAO.java`<br>`issueBlood()` | `SELECT units FROM blood_stock WHERE blood_group = ? FOR UPDATE` | Acquires an exclusive row-level lock on the blood group row in `blood_stock`. Prevents race conditions and double-spending when concurrent requests occur. | Show `StockDAO.java` line 92. Explain to the teacher how `FOR UPDATE` serializes concurrent transactions on the same blood group inventory row. |
| **Transaction Rollback Guarantee** | `StockDAO.java`<br>`issueBlood()` | `conn.rollback();`<br>`throw new BloodBankException(...)` | If requested units exceed available inventory, the entire transaction is rolled back and no stock is deducted. | **Run Main Option 13 (Issue Blood)**. Request 500 units when only 2 exist. Show rejection message and verify Option 12 stock was unchanged. |
| **Multi-Table INNER JOIN** | `DonorDAO.java`<br>`getDonationHistory()` | `SELECT ... FROM donors d JOIN donations dn ON d.donor_id = dn.donor_id ORDER BY dn.donation_date DESC` | Combines donor identity details with donation transaction logs. Excludes donors who have not yet donated. | **Run Main Option 14**. Point out that each line displays donor name, blood group, phone, and donation date combined from two separate tables. |
| **Relational VIEW (`LEFT JOIN` + `GROUP BY`)** | `schema.sql`<br>`donor_donation_summary` | `DonorDAO.java`<br>`getDonorSummary()` | Encapsulates complex reporting logic. `LEFT JOIN` guarantees that every donor appears—even those with 0 donations. `COALESCE(SUM(...), 0)` prevents nulls. | **Run Main Option 15**. Show how a newly added donor appears with `Total Donations: 0 | Total Units: 0` while active donors show accumulated totals. |
| **SQL Aggregations with `GROUP BY`** | `StockDAO.java`<br>`getDonationSummaryByGroup()` | `SELECT blood_group, COUNT(donation_id), SUM(units) FROM ... GROUP BY blood_group` | Aggregates summary statistics by category across large datasets using SQL aggregate functions (`COUNT`, `SUM`). | **Run Main Option 16**. Point to the summary table showing total donations and total units categorized by each blood group. |
